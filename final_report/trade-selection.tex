\section{Optimize and Evaluate Alternatives}
\label{section:optimize-and-evaluate-alternatives}
\label{sec:framework-trade-review}

This comparison recommends developing PA-CDT first under the declared priorities below. This remains a conditional engineering direction for the SysML/Python configuration. Deployment access and technical assessment are unresolved. It establishes neither procurement approval nor a measured winner. OOSEM connects analysis context and critical design properties to MOEs/MOPs. NASA decision analysis requires common criteria, alternatives, uncertainty and recorded rationale \citep[Sec.~17.3.6]{friedenthal2014practical} \citep[Sec.~6.8]{nasa2016systems}.

\subsection{Comparison basis and priorities}

Compare complete configurations on concept, requirements, design, model/software, change and review tasks and all 41 FRs. Use the same mission inputs, requirement/reference sets, model fidelity, numerical profiles, host software scope and raw-result comparison rules. First compare authoring/integration overhead with fixed specialist models. Then compare complete use under each declared configuration. Count manual work, access, maintenance, failed transfers, recovery and independent reconstruction. Incorrect outcomes earn no favorable effort assessment. Framework usage cost includes licences, compute/storage, APIs and maintenance over a dated period. EPS BOM/acquisition estimates remain separate.

Mandatory eligibility comes before preference: complete current allocation and active assistance, consistent checked exchanges, current authorized changes/releases/reviews, verified mandatory discipline/host profiles with explicit credibility limits, preserved/reconstructible raw evidence, and legal deployable access with export/recovery. These are acceptance conditions for later implementation assessment. Every candidate has a specified realization and unresolved verification. None has demonstrated eligibility. The two contrasting cases belong only to later validation/research evaluation. They impose no operational case-count gate.

The present design priorities are explicit qualitative judgments. First favor local authority over engineering meanings and current-context control. Next favor inspectable explanations, recoverable portable releases and replaceable analysis profiles. Retain workable collaboration and adoption as essential constraints. Reuse of existing services is valuable when it preserves these properties and reduces correct-task burden. These priorities are analyst proposals for stakeholder agreement. They are not measured weights or a utility function.

\subsection{Reasoned comparison and conditional direction}

PA-COM offers reusable shared parameter and Excel budget work. Its companion services must bridge requirement meaning, workbook settings and exact releases. PA-GY provides portable text with simpler storage, while adding nearly all engineering semantics and user guidance. PA-NS offers browser collaboration and dependency information, with maintained-stack, model/database consistency and planner-integration risks. PA-VS has the strongest source-supported complementary architecture/engineering-data workflow. Its demonstrated preliminary transfers do not establish recoverable full-lifecycle synchronization or active assistance. These distinctions explain retention without invented capability scores.

PA-CDT places requirements, EPS representations and interfaces in a locally checked SysML model. Python supplies explicit calculations, assistance and specialist mappings. Git and the managed archive preserve revisions and raw results independently of a changing hosted authoring service. This arrangement directly supports the declared priorities. It also carries substantial development and adoption work. SysML model editing/extension access, engineering quantity handling, semantic coverage, solver integration, profile availability, licensing, resource limits and clean replay remain open. Section~\ref{section:manage-requirements-traceability} describes the scope of specification consistency checks.

The conditional preference therefore concerns controllable development structure rather than claimed superior performance. PA-VS is the principal alternative if available services and verified synchronization offer lower correct-task burden while preserving authority, export and reconstruction. PA-COM remains relevant where COMET/Excel skills and access dominate. PA-NS remains relevant where concurrent browser work dominates. PA-GY remains relevant where portable text and a qualified contributor workflow dominate. No source-supported full EPS workflow is automatically eligible.

\paragraph{Verification and reversal criteria.}
Before retaining PA-CDT as the developed direction, establish legal deployment and extension access, native quantity/relationship fidelity, all mandatory discipline and selected host profiles, and reproducible model/software releases. Demonstrate active edit-linked assistance with independent expert references, explained corrections, eligibility changes, no-eligible cases, uncertain/truncated inputs, outage, cached superseded context and concurrent edits. Check coupled load/interface changes, interrupted exchanges, failed/partial analyses, exact unauthorized/stale coding attempts, separate calibration/assessment data, independent replay and current review authority. Apply the unchanged FR checks and risk-based MOP targets fixed before qualification.

Reverse or reopen the direction if a mandatory profile/access condition fails, if native representation loses engineering meaning, if response/currency/reconstruction targets cannot be met, or if correct-task burden makes the collaboration arrangement impractical. Compare the affected alternatives on the same tasks and resources. A documented PA-VS or other integration advantage can reverse the preference. Preserve dissent, raw outcomes and uncertainty. Quantitative benefit, prices, weights, sensitivity results and the empirical Pareto set remain unknown. No numerical optimization has been performed.

\paragraph{Information, state and procedures.}
The SysML configurations retain all five external ports and twelve logical exchanges. Advice inputs/results carry the exact context, question, applicable rules, source passages, model/rubric identities, raw scores, uncertainty, explanations and dispositions. Design inputs feed analysis. Raw outputs feed credibility and then phase-product assessment. Review records and changed dependencies feed configuration and assistance invalidation. All transfers preserve identity, quantity/unit, polarity and time/mode meaning. Incompatible raw submissions remain available without replacing controlled records.

SysML requirement/design/interface revisions are authoritative for PA-CDT engineering fields. L02 owns advice meaning, L06 credibility and L07 assessment/review meaning. Git/archive storage preserves those identified records. Current-context indexes and generated views can be rebuilt and create no competing baseline. Model records reside with N1, indexed source/advice records with N2, and released revisions, source packages and raw results with N3. Releases include model/solver/library/compiler dependencies, instructions, access limitations and result-specific comparison rules. Verify backups and independent restore/replay before claiming reconstruction.

L08 owns pending, current and stale assistance control. L07 owns draft, prepared, under review, accepted, conditional and blocked review control. The control conditions defined by the logical architecture require immediate edit invalidation, latest-context checks before presentation/application, exact current detailed-design authority before host work, current applicable supported results, and designated-authority review decisions. Physical source eligibility precedes shortlist explanations. Verified mandatory profiles precede admitted numerical execution. Missing or uncertain capability remains a recorded gap.

Operating procedures specify source/profile admission, field ownership, reviewed transfers, suggestion dispositions, calibration and independent assessment, exact design release, review decisions and recovery/replay. The Systems Engineer coordinates engineering procedures with qualified EPS/domain contributors. The designated review authority performs the decision procedure. Engineers approve requirement/design/model changes. Tools execute declared requests and grant no approval. Component verification needs include the assigned FR checks, interface round trips, authority/currency failures, source fidelity, model applicability and recovery. All procedures and component obligations remain proposed. No framework code or empirical V\&V result is supplied.
